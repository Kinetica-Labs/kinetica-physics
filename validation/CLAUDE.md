# Замеры и сравнение движков

Перенесено из корневого `CLAUDE.md`: грузится, когда работа идёт с файлами этого каталога.

## Ворота правки (`validation/gate.py`)

```
python3 validation/gate.py --remote     # перед коммитом: всё «да/нет» + мерки с эталоном, скорость — на свободной машине
python3 validation/gate.py --quick      # промежуточный шаг правки (без clang++, таблицы случаев, разброса стены, сцен сравнения)
python3 validation/gate.py --remote --update   # записать эталон: только когда итог понят и объяснён в журнале
python3 validation/gate.py --accept     # то же числами только что сделанного прогона, без нового замера
```

Итог один: ХУЖЕ (код выхода 1), НЕ ХУЖЕ или ЛУЧШЕ; эталон — `docs/reports/data/gate-baseline.json`. Правка
принимается, только если итог не ХУЖЕ; ухудшение, на которое идут сознательно, записывается `--update` и
объясняется в `docs/JOURNAL.md`. Скорость на рабочей машине не мерить: тот же код давал здесь ±4 % тактов и
+6…9 % времени кадра из-за соседних программ — без `--remote` порог скорости 6 % и ловит только грубую
порчу. Свободная машина — Windows, clang (llvm-mingw), другой процессор: заодно это третья платформа, на
которой хэш обязан совпасть. Связь с ней — сценарии `build/remote/sync.sh` и `rrun.sh` (вне git: в них адрес
и пароль); если их нет, спросить у пользователя адрес машины. Там наименьшее из десяти прогонов на
закреплённом ядре повторяется до 0,1 %; незакреплённый прогон гуляет на 5 %. У её процессора кэш 30 МБ:
ожидания памяти, которое на рабочей машине съедало до 29 % тактов, там нет, и правка ради памяти (подкачка
H81) на ней не видна — такие правки мерить ещё и здесь, `compare_cycles.sh`.

Ворота проверены намеренной порчей кода (2026-11-21): вход в набор по одной точке — ХУЖЕ по перекрытию
стоящей пирамиды; разложение с нуля на каждом шаге — ХУЖЕ по кадрам рывка (48–68 мс против 18–23); пустой
цикл в проходе нормалей — ХУЖЕ по пирамиде из 1 015 кубов (+5,4 % при пороге 3 %). Новую мерку добавлять
вместе с поломкой, которую она ловит.

Рывок куба, как в окне, — `study-window-pull [exact|realtime] [сцена] [тело] [скорость] [dx dy dz]`:
медиана, 99-й процентиль и наибольший кадр за 240 кадров, скорость тел и перекрытие. Смотреть хвост, а не
среднее: окно подвисает на отдельных кадрах при медиане 1–3 мс.

## Приборы (`validation/studies/`)

`KP_SLEEP=1` включает сон островов в `study-standard-scenes`.
Ключи приборов — переменные окружения `KP_*`, перечислены в шапке каждого `validation/studies/*.cpp`.
Библиотека читает из окружения только `KP_STEP_MEMORY`; `KP_THREADS` разбирает сам прибор
(`WorkerPool::shared().resize(n)`) — новый прибор обязан делать то же, иначе хэш по потокам не проверить.
Время кадра в окне меряется `KP_PACED=1 study-frame-times`: в темпе окна ядра между кадрами сбрасывают
частоту (профиль питания `balanced`), и шаг стоит в 2–3 раза дороже, чем при счёте подряд.
Перекрытие сцены с ударами (куча, чаша) с одного прогона — случайное число: сцена хаотична. Мерить
его `study-overlap-spread` — медианой и наибольшим по 16 вариантам с возмущением скоростей 1 мм/с.

## Приборы скорости

```
./build/validation/studies/study-overlap-spread [ключ_сцены] [секунды] [вариантов]
./build/validation/studies/study-scale [тел ...]        # цена кадра от числа тел: порознь, столбики, кладка
./build/validation/studies/study-frame-times [ключ_сцены] [секунды]   # рывки: медиана, 99 %, наибольший кадр
KP_THREADS=1 ./build/validation/studies/study-frame-stages pyramid3d  # кадр по стадиям шага: куда уходит время
KP_THREADS=1 BENCH=14 perf stat -e cycles:u,instructions:u,LLC-load-misses:u build/validation/engines/compare-ours realtime 8
                                                        # счётчики вместо времени: такты шумят на 2–3 %, время — на 20 %;
                                                        # perf работает при kernel.perf_event_paranoid ≤ 1 (сбрасывается перезагрузкой)
./build/validation/studies/study-allocations [ключ_сцены] [секунды]   # обращений к куче на кадр; KP_SITES=1 — откуда
```

Скорость мерить попеременно: `validation/compare_cycles.sh <было> <стало>` — пары прогонов на закреплённом
ядре, наименьшее число тактов; различает около 1 % (один прогон гуляет на 15 % от частоты и соседей).
Замер `BENCH` идёт 60 кадров. Число инструкций время не задаёт: половина тактов — ожидание исполнения.
Сводке `perf stat --topdown` не верить (дала 29 % сброшенной работы при настоящих 3 %): брать первичные
события с меткой `:u` — `uops_issued.any`, `uops_retired.slots`, `topdown.slots`, `cycle_activity.*`.
Правке ради скорости предшествует замер, где теряются такты: 2026-11-20 шесть правок по догадке
(H70, H73, H74, H76, H77) были сделаны и откатаны. Отклонённое — в `validation/attempts.jsonl`.

## Сравнение с Box3D и RP3D (`validation/engines/`)

`validation/engines/` — общие сцены (покой, осыпь, тело в теле, сон, высокий столбик, сочленения) для нашего движка (`compare-ours`, в сборке), Box3D и RP3D
(собираются из `research/refs`, рецепт в шапке файла); `SCENE=ключ compare-ours …` — одна сцена. Каждая сцена идёт в 16 вариантах с малыми
возмущениями; «лучше Box3D» — только по критерию знаков на парах вариантов, не по одному прогону.
Дрожь меряется по всем кадрам после успокоения (скорость точки, развороты, пробуждения), а не по
последнему: глаз видит мигание сна и дёрганье при нулевой средней скорости. Перекрытие тел —
глубиной по разделяющим осям (`overlap_mm`): CCD быстрого шага (упреждающие контакты) спасает от
пролёта, но не от опоры, которую проходы решателя не донесли по длинной цепочке.

`research/refs` (клоны Box3D и ReactPhysics3D, вне git) — символическая ссылка наружу; если она пропала —
`python3 research/facts.py restore`.
