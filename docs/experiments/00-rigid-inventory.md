# Опись `phys_realflow/src/rigid` и кандидаты на абляцию

Снято 2026-11-14 с `phys_realflow@ed7c308` (ветка `arm-skills`, в рабочей копии есть
незакоммиченные правки документов). **Это опись по именам файлов, переключателям `RigidParams`
и комментариям при них — не аудит кода.** Отнесение файла к группе сделано по имени; где
это догадка, стоит «?». Вердиктов здесь нет: правый столбец — вопрос, на который должно
ответить исследование или прогон.

Два наблюдения, видимые уже из размеров:

- **Разрушение — почти четверть «твёрдых тел», но это не ядро.** Удалять его незачем, а вот
  жить ему естественнее отдельным модулем поверх ядра: ядро станет на 23 % меньше без потери
  возможностей.
- **`RigidWorld` — 1430 строк и около полусотни параметров в `RigidParams`.** Один класс знает
  про решатель, CCD, сон, трение, диагностику энергии и работу моторов. Это главный кандидат
  на разделение при переходе к читаемому ООП.

## Целевое ядро: «компактное, но полное»

Охват — только твёрдое тело. «Полное» значит: в каждой подсистеме ровно один механизм,
и ни одна подсистема не пропущена. Сейчас в большинстве ячеек их два-четыре.

| Подсистема | Нужен один | Сейчас в `src/rigid` |
|---|---|---|
| Формы | сфера, бокс, капсула, цилиндр, выпуклая оболочка, составная, статическая сетка | есть все |
| Поиск пар | одна структура | четыре за Strategy |
| Точки контакта | один путь на пару форм + одно правило редукции | аналитика + SAT + GJK/EPA + запасной путь возмущениями |
| Перенос между шагами | один кэш | `ContactCache` + `ContactPatch` + перенос по силе и моменту |
| Решатель | один | последовательные импульсы + XPBD + вариационный удар |
| Позиционная ошибка | один способ | Baumgarte + split impulse + позиционный проход суставов + доводка невязки |
| Трение | один конус | квадрат и диск + пять добавок |
| Сочленения | один набор типов, один способ решения | шесть типов; только максимальные координаты |
| Быстрые тела | один способ | conservative advancement + откат шага + спекулятивный запас |
| Острова и сон | один | union-find + сон + демпфирование покоя |
| Запросы сцены | луч, заброс формы, перекрытие | не описано (отдельное дерево мира в `src/spatial`) |

Разрушение (2 720 строк) в ядро не входит — выносится поверх него.

## Кандидаты на абляцию

Каждая строка — механизм с собственным переключателем. Порядок — от самых дорогих по строкам
и по времени шага.

| Механизм | Переключатель и умолчание | Что компенсирует | Вопрос |
|---|---|---|---|
| Обнаружение столкновений на каждом подшаге | `substeps = 10`, `contactReuseSubsteps = 1` | — | Комментарий в коде сам ссылается на Box2D v3: «collides once per step and relaxes over substeps». Не здесь ли разрыв 0,55 мс против 0,03 мс у Jolt? Что делают Box3D и Jolt при 1 и при N подшагах? |
| Split impulse | `splitImpulse = true`, `baumgarte = 0.2`, `slop` | позиционную ошибку | В коде честно: «potential energy can change»; это и есть зафиксированный джиттер. Заменяет ли мягкое ограничение + relax (Box3D) сразу split impulse и Baumgarte? |
| Shock propagation | `shockPropagation = true`, `shockFriction = true`, `shockIterations = 2`; 326 строк | стопки, отношение масс | Есть ли аналог хоть в одном движке уровня A? Нужен ли он при подшагах с мягким контактом? |
| Доводка невязки | `contactRefinementIterations = 48`, два допуска; 228 строк | недосходимость последовательных импульсов | Если основной решатель сходится, этот слой не нужен. Сколько сцен ломается при `0`? |
| Блочный LCP многообразия | `blockSolver = true`, `manifoldIterations = 4`, `blockCfm = 1e-3` | 4 компланарные точки | Кто из движков решает нормали блоком в 3D, а кто обходится без него? |
| Решатель XPBD | `RigidSolver::XPBD` + `collisionInterval`, `positionIterations`; 279 строк | — (помечен experimental) | Проходит ли он хоть один тест `rf_verify`, которого не проходит основной? Если нет — удалить вместе с тремя параметрами. |
| Вариационный удар | `VariationalImpactStep` + `VariationalFlight`; 326 строк | — (только сферы) | То же: что он даёт, чего нет у основного пути? |
| Две модели трения | `circularFriction = false` — «legacy square approximation» | — | Зафиксированная боль √2·μN. Оставить одну модель: диск. Что ломается? |
| Статическое трение, порог прилипания, запирание вращения, качение, кручение | `staticFriction`, `stickVelocity`, `rotationalLock = true`, `rollingResistance`, `twist` | покой на склоне, колёса | Пять механизмов вокруг одного конуса. Какой минимальный набор у MuJoCo (`condim` 1/3/4/6) и Box3D? |
| Четыре broadphase за Strategy | SAP по умолчанию + перебор, BVH/SAH, динамическое дерево; 308 строк | — | Какой один выбирают Box3D, Jolt, PhysX, Rapier — и почему? Оставить один. |
| CCD: conservative advancement + атомарный шаг с откатом | `ccd = true`, `ccdAllMoving`, `ccdSkipContactPairs`, `ccdMaxSubdivisions = 16`; 925 строк | туннелирование | Боль: пролёт сквозь плиту-меш и потеря энергии при дроблении. Хватает ли спекулятивных контактов (Box3D) без отката всего шага? |
| Демпфирование покоя | `restDamping`, `restLinearThreshold`, `restAngularThreshold` поверх `linearDamping` и `sleeping` | дрожание покоящихся тел | Нужно ли оно, когда исчезнет джиттер от split impulse? |

### Удаляется без исследования

Параметры и поля, про которые в самом коде написано, что они остались ради совместимости:
`ccdMaxPasses` («retained for source compatibility»), `ToiResult::hit` («compatibility»),
`passLimitReached` («legacy clamping diagnostic»), квадратное трение («legacy»). Это долг,
а не возможности.

## Первые ответы (поиск по клонам, 2026-11-14)

Поиск по именам в исходниках одиннадцати клонов (`box3d`, `box2d`, `solver2d`, `jolt`,
`rapier`, `parry`, `bepu`, `bullet3`, `physx`, `mujoco`, `drake`; коммиты — в
`research/data/sources.jsonl`). Оговорка: это поиск слова, а не приёма — тот же приём под другим
именем он не найдёт.

- **Shock propagation.** `rg -i 'shock.?propagat'` — ноль файлов во всех одиннадцати.
  Ни один из этих движков не держит прохода с таким названием; у нас это 326 строк и три
  параметра. Вопрос к абляции сужается до одного: какие наши сцены без него падают.
- **Блочный решатель нормалей.** `rg -i 'block.?solver|block solve'`:
  - `box3d/src`, `jolt/Jolt`, `bepu/BepuPhysics` — совпадений нет;
  - `box2d/src` — только в суставах (`prismatic_joint.c:295`, `weld_joint.c:283`), в контактах нет;
  - `rapier` — есть, но за необязательным флагом сборки `block-solver`
    (`src/dynamics/solver/contact_constraint/contact_with_twist_friction.rs:381`) с проверкой
    обусловленности `BLOCK_SOLVER_MIN_CONDITION`;
  - `solver2d` — отдельный вариант `solve_pgs_ngs_block.c`, один из сравниваемых, не итоговый.

  То есть блочное решение контактов в этих движках — исключение или опция, а не умолчание.
- **Какой один broadphase.** Прочитаны места выбора по умолчанию; факты со строками — в
  `research/data/facts/{jolt,rapier,physx,bepu,bullet3}.jsonl`, сводка — `research/tables/matrix.md`.

  | Движок | Умолчание | Где |
  |---|---|---|
  | Jolt | четверичное дерево `BroadPhaseQuadTree`; перебор — закомментированная отладочная замена | `Jolt/Physics/PhysicsSystem.cpp:47` |
  | Rapier | `BroadPhaseBvh` — единственная реализация | `src/geometry/mod.rs:96` |
  | Bepu | два дерева: `ActiveTree` и `StaticTree` | `BepuPhysics/CollisionDetection/BroadPhase.cs:35` |
  | Bullet | умолчания у библиотеки нет; примеры и сервер PyBullet берут `btDbvtBroadphase` | `examples/CommonInterfaces/CommonRigidBodyBase.h:62` |
  | PhysX | `ePABP` — параллельный box pruning; SAP оставлен как выбор «когда почти всё спит» | `physx/include/PxSceneDesc.h:1042` |

  Четыре из пяти выбрали дерево, ни один не ставит по умолчанию инкрементальный SAP — а у нас
  по умолчанию именно он. Rapier к тому же строит запросы сцены (`QueryPipeline`) поверх того
  же дерева, что ищет пары; у нас для запросов отдельное дерево в `src/spatial`. Box3D — в
  карточке пилота.
- **Столкновения раз за шаг.** Jolt: `Update(inDeltaTime, inCollisionSteps, …)` — столкновения
  ищутся раз на шаг столкновений, внутри 10 скоростных и 2 позиционные итерации
  (`Jolt/Physics/PhysicsSettings.h:84`, `:87`). У нас 10 подшагов, и на каждом — полный поиск
  столкновений. Что именно съедает время, покажет профиль, но разница в объёме работы видна
  уже из умолчаний.

## Как проводить абляцию

1. Один механизм за раз: выключить → `rf_verify` + стандартные сцены (`docs/15`) → записать, что
   изменилось в числах. Механизм, выключение которого ничего не меняет, удаляется.
2. Механизм, который что-то держит, сначала получает замену из исследования, потом удаляется.
3. Работать в отдельном `git worktree` от `phys_realflow`: в основной копии сейчас идёт ветка
   `arm-skills` с незакоммиченными правками, её трогать нельзя.
4. Числа до и после — в `evidence/` по соглашениям `phys_realflow`.

Правок в `phys_realflow` пока не было: это отдельный шаг после пилота исследования.
